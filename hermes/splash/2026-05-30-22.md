## 1. 🟢 HSV COLOR FILTERING — TEAM JERSEY IDENTIFICATION

### Specific HSV Ranges (OpenCV Scale: H 0-179, S 0-255, V 0-255)

| Team Color | Mask | Lower Bound (H,S,V) | Upper Bound (H,S,V) | Notes |
|---|---|---|---|---|
| **Red** | Lower Range | `[0, 70, 50]` | `[10, 255, 255]` | Bright reds, orange-reds |
| **Red** | Upper Range | `[170, 70, 50]` | `[179, 255, 255]` | Deep red, crimson |
| **Blue** | Single Range | `[100, 70, 50]` | `[140, 255, 255]` | Sky blue to dark navy |

### Critical Insight: Red Wraps Around Hue 0/180
Red is split across two ranges in OpenCV because the hue circle wraps. Both masks must be combined with `cv2.bitwise_or()`.

### Python Implementation

```python
def create_team_masks(hsv_frame):
    # Red team (dual mask — hue wraps around)
    lower_red1 = np.array([0, 70, 50])
    upper_red1 = np.array([10, 255, 255])
    lower_red2 = np.array([170, 70, 50])
    upper_red2 = np.array([179, 255, 255])
    mask_red = cv2.bitwise_or(
        cv2.inRange(hsv, lower_red1, upper_red1),
        cv2.inRange(hsv, lower_red2, upper_red2)
    )
    
    # Blue team (single range)
    lower_blue = np.array([100, 70, 50])
    upper_blue = np.array([140, 255, 255])
    mask_blue = cv2.inRange(hsv, lower_blue, upper_blue)
    
    # Morphological cleanup
    kernel = np.ones((5,5), np.uint8)
    mask_red = cv2.morphologyEx(mask_red, cv2.MORPH_OPEN, kernel)
    mask_blue = cv2.morphologyEx(mask_blue, cv2.MORPH_OPEN, kernel)
    
    return mask_red, mask_blue
```

### Lighting Adaptation for Drone Footage
| Condition | Adjustment |
|---|---|
| Shadows (players under trees) | Drop V minimum from 50 → 30 |
| Overexposure (midday sun, washed-out jerseys) | Drop S minimum from 70 → 50 |
| Noise (grass, stadium lines, ground texture) | Apply MORPH_OPEN with 5×5 kernel |
| Small false positives | Filter by contour area: `cv2.findContours()` + minimum area threshold |

### Pipeline Integration
The recommended approach is a **hybrid pipeline**: YOLO person detection → crop person bounding box → apply HSV color mask on cropped region → classify jersey color. This is more robust than running HSV on the full frame because:
- Eliminates background color bleed (grass, sky, ground)
- Only processes within detected person bounding boxes (~2ms per box)
- Works regardless of where the person is in the frame

### Depth Anything V2 is the Winner for Splash
- Metric depth variant natively predicts scale-aware depth in meters
- Can run at 25-35 FPS alongside YOLO at 85-110 FPS on M3 — fits within the <50ms total pipeline target
- Core ML conversion available for Apple Neural Engine optimization

### Recommended Implementation: Median Bounding Box Depth

```python
# Pseudocode for depth extraction
device = torch.device("mps" if torch.backends.mps.is_available() else "cpu")

# Run YOLO detection → get person bounding box
# Run Depth Anything V2 on frame → get depth map
# Crop depth map to person bounding box
person_depth = depth_map[y1:y2, x1:x2]
# Use MEDIAN (not mean) to eliminate edge noise
distance = torch.median(person_depth)
```

**Key insight:** Using **median** depth over the bounding box eliminates noise from background edge bleed during drone motion — a proven technique from the research community.

### Fallback: Mono+PnP (Known Height Method)
If depth estimation is too compute-heavy, use the known human height method:
```
Z = (H × f) / h
```
Where H = 1.7m (avg human height), f = camera focal length (known), h = pixel height of bounding box.

**Accuracy:** ±0.5m at 5m range — marginal but acceptable for Splash's 3m engagement distance.

## 4. 🟢 OPTICAL FLOW + KALMAN FILTER HYBRID TRACKING

### Core Comparison

| Feature | Lucas-Kanade Optical Flow | Kalman Filter | Combined |
|---|---|---|---|
| **Primary Role** | Visual feature tracking | Kinematic state prediction | Robust object tracking |
| **Drone ego-motion** | ❌ Fails (mistakes drone movement for target) | ✅ Handles well (constant velocity model) | ✅ Highly resilient |
| **Occlusions** | ❌ Fails completely | ✅ Maintains track (predicts path) | ✅ Recovers track after occlusion |
| **Computational cost** | High (scales with resolution) | Extremely low (matrix mult on few vars) | Balanced |
| **Typical FPS (Python/OpenCV)** | 30-60 FPS | >500 FPS | **45-90 FPS (optimized)** |

### Recommended Architecture: Kalman-Guided LK Search

```
[Frame N] → Run LK inside Kalman search window → [Measurement Vector]
                                                         │
                                                         ▼
[Frame N+1] ← Update BBox ← Predict next state ← Correct Kalman state
```

1. **Prediction:** Kalman predicts where the person will be next frame
2. **Measurement:** LK optical flow only searches WITHIN the predicted bounding box (not full frame)
3. **Correction:** Actual optical flow coordinates correct the Kalman kinematic model

### Implementation

```python
# Kalman Filter (4 dynamic states: x, y, dx, dy; 2 measurements: x, y)
kf = cv2.KalmanFilter(4, 2)
kf.transitionMatrix = np.array([[1,0,1,0],
                                [0,1,0,1],
                                [0,0,1,0],
                                [0,0,0,1]], dtype=np.float32)
kf.processNoiseCov = np.eye(4, dtype=np.float32) * 0.03
kf.measurementNoiseCov = np.eye(2, dtype=np.float32) * 0.5

# LK parameters (for tracking features within person bounding box)
LK_PARAMS = dict(winSize=(15, 15), maxLevel=2,
                 criteria=(cv2.TERM_CRITERIA_EPS | cv2.TERM_CRITERIA_COUNT, 10, 0.03))
```

### Optimization for M3:
- Downscale optical flow frame to 320×240
- Limit feature points to 10-30 high-quality Shi-Tomasi corners
- Keyframe re-detection every 15-30 frames to prevent drift
- Use Kalman prediction as fallback during occlusions (target runs behind tree)

## 5. 🟢 Maxboels/TrackingPanTiltCam — REFERENCE ARCHITECTURE

### Two Modes (Directly Map to Splash)

| Mode | Buffer | Weighting | Use Case | Maps to Splash |
|---|---|---|---|---|
| **Surveillance** | 10-frame history | Equal weighting (rolling mean) | Keep target in frame, smooth adjustments | ORBIT scanning mode |
| **Turret** | 3-frame history | **Exponential decay** (prefers newest) | Rapid response, precise alignment | TRACK & FIRE mode |

### Motion Compensation — Critical for Drone

The system prevents **positive feedback loops** caused by camera movement:

```
Δθ_true = Δθ_apparent + Δθ_camera
```

- **Δθ_apparent:** Pixel offset between frames (measured by YOLO)
- **Δθ_camera:** Physical angle commanded to servo during that frame
- **If Δθ_true ≈ 0:** Target is stationary → dampen servo output (prevent oscillation)

**Pixel-to-Angle Mapping:**
```python
deg_per_px_x = camera_hfov / frame_width   # e.g., 60° / 640px = 0.094°/px
deg_per_px_y = camera_vfov / frame_height  # e.g., 45° / 480px = 0.094°/px
```

### Static Confidence Dampening
When `Δθ_true < 0.5°` threshold for consecutive frames, the system increases `static_confidence` (0.0→1.0) and applies dampening factor `(1.0 - 0.5 × static_confidence)` to servo output. This prevents micro-oscillations when tracking a stationary target.

### Architecture for Splash

```
[USB Camera / Hawkeye UVC] → [YOLOv12n] → [Kalman Filter] → [Motion Comp] → [MAVLink SERVO_SET]
```

Splash replaces the Arduino serial with MAVLink `SERVO_SET` commands to the ESP32 → FC UART → PWM5/PWM6.

## 6. ⚠️ YOLOv12 "ATTENTION TAX" — REFINED PERFORMANCE ESTIMATE

### Critical Finding: YOLOv12 May Underperform YOLOv11 on M3

Previous estimates (Cycle 2) suggested 85-110 FPS for YOLOv12n on M3. New research reveals:

| Architecture | vs YOLOv11 (CNN-based) | FPS Impact on M3 |
|---|---|---|
| YOLOv12 (Attention-centric) | **15-25% slower** | 85-110 FPS → **~60-85 FPS** estimated |
| YOLOv11 (Pure CNN) | Baseline | ~75-80 FPS (confirmed Cycle 2) |

**Root cause:** YOLOv12 uses FlashAttention + Area Attention. On MPS (Apple Silicon), FlashAttention CUDA kernels don't map directly — they require Metal GPU shader equivalents that may not be fully optimized.

**Recommendation:**
1. **Benchmark both** YOLOv11n and YOLOv12n on the actual M3 MacBook before committing
2. If YOLOv12 FlashAttention is slow on MPS, fall back to **YOLOv11n** (~75-80 FPS) — still well above the 30 FPS pipeline target
3. YOLOv13's HyperACE mechanism may add further overhead — test carefully

### ByteTrack Integration

The `ultralytics` API supports ByteTrack natively:
```python
results = model.track(source=frame, tracker="bytetrack.yaml", 
                      persist=True, classes=[0], verbose=False)
```

- `persist=True` maintains track memory across frames
- `classes=[0]` filters for persons only (COCO class 0)
- ByteTrack's BYTE association uses low-confidence boxes in second-stage matching — important for drone footage where motion blur reduces detection confidence

|---|---|---|

## 8. 🟢 JONATHAN RANDALL REFERENCE — ARCHITECTURE DOCUMENTED

### System Architecture
```
+----------------+  MJPEG HTTP (WiFi)    +--------------------+
|   ESP32-CAM    | ==================>   |   Python Host PC   |
| (Video Server) |                       | (YOLO + Tracking)  |
+----------------+                       +--------------------+
       ^                                          |
       |  HTTP GET /control?pan=X&tilt=Y&fire=Z   |
       +==========================================+
```

### Key Technical Details

| Parameter | Value | Relevance to Splash |
|---|---|---|
| Resolution | 320×240 (QVGA) | Low enough for stable WiFi streaming |
| JPEG quality | 12 (0-63, lower = better) | Balances quality vs bandwidth |
| Frame rate | ~15-25 FPS at QVGA | Matches Splash WiFi bandwidth limit |
| Servo control | HTTP GET parameters | Splash uses MAVLink SERVO_SET instead |
| Pump control | GPIO relay | Splash uses MOSFET (IRFZ44N) |
| Tracking | Proportional-only (Kp only) | Splash uses full PID + Kalman |

### Lessons for Splash
1. **Power isolation critical:** Water pump and servos MUST be on separate battery with common ground. Peak draw from pump relay causes ESP32 brownout resets.
2. **320×240 is the sweet spot:** Higher resolution introduces WiFi frame drops and mechanical latency.
3. **Proportional-only control is too simplistic:** The reference uses `pan += 1 if error_x > 0 else -1` — no damping, no integral term. Splash's full PID + Kalman is significantly more sophisticated.
4. **Deadzone of 15px is correct:** Prevents servo jitter when target is near center.
