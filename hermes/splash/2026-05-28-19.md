## 2. 🔴 HSV Color Filtering for Team Jersey Identification

### 2.1 Why HSV Works for Splash
Senior Assassins uses colored armbands or jerseys to identify teams. HSV separates color (Hue) from lighting (Value), making it robust to shadows and sun glare — both common in outdoor drone footage.

### 2.2 Red vs Blue HSV Ranges (OpenCV)

```python
import cv2
import numpy as np

# RED — wraps around 0/180 in OpenCV Hue wheel
lower_red1 = np.array([0, 70, 50])
upper_red1 = np.array([10, 255, 255])
lower_red2 = np.array([170, 70, 50])
upper_red2 = np.array([180, 255, 255])

# BLUE — straightforward single range
lower_blue = np.array([100, 70, 50])
upper_blue = np.array([130, 255, 255])

# Apply masks
mask_red = cv2.bitwise_or(
    cv2.inRange(hsv, lower_red1, upper_red1),
    cv2.inRange(hsv, lower_red2, upper_red2)
)
mask_blue = cv2.inRange(hsv, lower_blue, upper_blue)
```

### 2.3 Lighting Robustness for Drone Footage

Drone tracking introduces severe shadows, sun glare, and changing exposure. Three crucial optimizations:

1. **Adaptive Value Thresholding**: Don't use static lower bounds. Dynamically calculate frame average brightness and shift `V_min = max(30, avg_brightness - 50)`.
2. **CLAHE Pre-processing**: Apply Contrast Limited Adaptive Histogram Equalization to the V channel before filtering to normalize shadows.
3. **Morphological Closing**: Use `cv2.morphologyEx(mask, cv2.MORPH_CLOSE, kernel)` to bridge gaps in jersey color caused by sunlight reflections or kit patterns.

### 2.4 Histogram Backprojection for Complex Kits

When jerseys have mixed patterns (stripes, sponsors), basic HSV masks lose accuracy. Histogram backprojection calculates the probability that a pixel belongs to a target team based on a reference image:

```python
# Reference histogram from cropped jersey template
roi_hsv = cv2.cvtColor(jersey_template, cv2.COLOR_BGR2HSV)
roi_hist = cv2.calcHist([roi_hsv], [0, 1], None, [180, 256], [0, 180, 0, 256])
cv2.normalize(roi_hist, roi_hist, 0, 255, cv2.NORM_MINMAX)

# Project onto target frame
frame_hsv = cv2.cvtColor(current_frame, cv2.COLOR_BGR2HSV)
prob_map = cv2.calcBackProject([frame_hsv], [0, 1], roi_hist, [0, 180, 0, 256], 1)
```

### 2.5 Color Re-Identification Pipeline

When spatial tracker loses a player (occlusion, drone movement), use Bhattacharyya distance via `cv2.compareHist(hist1, hist2, cv2.HISTCMP_BHATTACHARYYA)` to compare lost player's cached HSV histogram against newly detected unassigned bounding boxes. Match if distance < 0.35.

```
[Drone Video Frame] → [YOLOv11n Bounding Boxes] → [Crop Player ROIs]
                                                          │
[Spatial ID Assigned] ← [Hungarian Matching] ← [Compare HSV Histograms (Bhattacharyya)]
```

## 4. 🔴 Motion Compensation — Preventing Feedback Loops

### 4.1 The Core Problem
When a pan-tilt camera on a drone moves to track a target, the camera's own movement creates apparent "ego-motion" in the video feed. If the tracking system mistakes this self-induced motion for actual target movement, it overcorrects → severe oscillations → tracking failure.

### 4.2 Solution Architecture

```
┌─────────────────┐     ┌─────────────────┐
│   Onboard IMU   │     │   Camera Frame  │
│ (High-Freq Gyro)│     │ (Optical Flow)  │
└────────┬────────┘     └────────┬────────┘
         │                       │
         ▼                       ▼
┌─────────────────┐     ┌─────────────────┐
│ Rotation Matrix │     │ Background      │
│     R_cam       │     │ Motion Field    │
└────────┬────────┘     └────────┬────────┘
         │                       │
         └───────────┬───────────┘
                     ▼
          ┌─────────────────────┐
          │  Homography Warping │
          │  (Cancels ego-motion)│
          └──────────┬──────────┘
                     ▼
          ┌─────────────────────┐
          │ Pure Target Motion  │
          │ Vector (True Error) │
          └─────────────────────┘
```

### 4.3 Three-Layer Compensation Strategy

1. **IMU Gyro Feedforward**: High-frequency gyroscope measures exact pan-tilt angular velocity between frames. Calculate expected visual shift from camera rotation BEFORE the next frame is processed.
2. **Optical Flow Subtraction**: `F_target = F_total - F_ego` — subtract predicted ego-motion from total optical flow to isolate target motion.
3. **Hysteresis Deadband**: Implement spatial deadband to prevent servo twitching from sub-pixel noise:
```python
if abs(new_pixel_error - old_pixel_error) < deadband_threshold:
    servo_command = old_servo_command  # Clamp to prevent jitter
```

### 4.4 Edge-Case Mitigation

| Challenge | Root Cause | Mitigation |
|-----------|-----------|------------|
| High-frequency jitter | Servo lag + frame vibrations | Low-pass filter on flow vectors + mechanical damping |
| Motion blur failure | Rapid pan-tilt adjustments break feature matching | Switch to IMU-driven tracking until clarity returns |
| Target loss at limits | Mechanical pan-tilt limits reached | Command drone yaw rotation when servo axis saturates |

### 4.5 Splash-Specific Implementation
For Splash, motion compensation is CRITICAL because:
- The drone itself is moving (not just the pan-tilt servos)
- ArduPilot provides IMU data via MAVLink (gyro rates, attitude)
- The ESP32 WiFi bridge can forward IMU telemetry to the MacBook CV pipeline
- MAVLink `ATTITUDE` messages arrive at 10-50Hz — sufficient for gyro-aided compensation

## 5. 🔴 Kalman Filtering for Smooth Tracking

### 5.1 Why Kalman for Splash
- **Predicts target position** based on estimated velocity during brief occlusions (person behind tree)
- **Reduces jitter** while maintaining responsiveness for moving targets
- **Maintains tracking** when YOLO misses a few frames
- **Fuses** bounding box center (measurement) with motion model (prediction)

### 5.2 Linear Kalman Filter — 2D Implementation

The state vector tracks position and velocity: `x = [px, py, vx, vy]`

**Prediction step:**
```python
def predict(self):
    self.x = np.dot(self.F, self.x)  # F = state transition matrix
    self.P = np.dot(self.F, np.dot(self.P, self.F.T)) + self.Q
```

**Update step:**
```python
def update(self, z):  # z = bounding box center measurement
    z_hat = np.dot(self.H, self.x)
    y = z - z_hat                         # Innovation
    S = np.dot(self.H, np.dot(self.P, self.H.T)) + self.R  # Innovation covariance
    K = np.dot(self.P, np.dot(self.H.T, np.linalg.inv(S)))  # Kalman Gain
    self.x = self.x + np.dot(K, y)        # Corrected state
    self.P = np.dot((I - np.dot(K, self.H)), self.P)  # Corrected covariance
```

### 5.3 Parameter Tuning for Splash

| Parameter | Turret Mode Value | Effect |
|-----------|------------------|--------|
| `INIT_POS_STD` | 10 | Initial position uncertainty (pixels) |
| `INIT_VEL_STD` | 10 | Initial velocity uncertainty (pixels/s) |
| `ACCEL_STD` | 20-40 | Process noise — higher = trust measurements more |
| `GPS_POS_STD` | 3-5 | Measurement noise (YOLO bounding box jitter) |

**Critical insight from yudhisteer's UAV Kalman project**: For dynamic non-linear systems (person changing direction), use HIGH `ACCEL_STD` (20-40) to make the filter trust measurements (YOLO detections) more than the linear motion model. This prevents prediction lag when targets change direction suddenly.

### 5.4 Extended Kalman Filter (EKF) for Drone Integration
For Splash, an EKF can fuse:
- YOLO bounding box center (vision measurement)
- IMU gyro rates (ego-motion compensation)
- MAVLink drone position (camera frame of reference)

The maxboels TrackingPanTiltCam provides a working Kalman implementation with mode-switching (surveillance vs turret) that can be adapted directly.

## 6. 🟡 Multi-Person Tracking — Identifying the Primary Target

### 6.1 Tracker Framework Comparison

| Feature | ByteTrack | DeepSORT | StrongSORT |
|---------|-----------|----------|------------|
| **Primary Mechanism** | IoU matching | Kalman + Re-ID | Advanced Kalman + Strong Re-ID |
| **Drone Suitability** | **Excellent** ✔ | Poor ✘ | Moderate |
| **Low-Score Detection** | KEEPS (critical for occlusion) | Discards | Discards |
| **Compute Overhead** | Extremely Low | Medium | High |
| **Viewpoint Robustness** | Good (pure spatial) | Bad (top-down breaks Re-ID) | Bad (slow) |

### 6.2 Why ByteTrack Wins for Splash
1. **Keeps low-confidence detections** — When a target is partially occluded by a tree, YOLOv11n outputs lower confidence. ByteTrack still matches these boxes instead of discarding them.
2. **Pure IoU matching** — No heavy Re-ID network. Runs at negligible cost alongside YOLOv11n.
3. **Top-down viewpoint robust** — DeepSORT's appearance embeddings fail when everyone looks like "head + shoulders" from above. ByteTrack doesn't care about appearance.

### 6.3 Primary Target Selection — Priority Score Function

Once ByteTrack assigns IDs, the "primary target" is selected using a priority score:

```
P = w1 · S_conf + w2 · (1 - D_center) + w3 · I_IoU
```

Where:
- **S_conf**: Detection confidence score
- **D_center**: Normalized distance from target center to frame center
- **I_IoU**: IoU with Kalman-predicted position from previous frame
- **w1, w2, w3**: Altitude-dependent weights

### 6.4 Target Selection Modes for Splash

| Mode | Selection Method | Splash Use Case |
|------|-----------------|-----------------|
| **Geofencing / Point-and-Click** | Operator selects pixel → nearest Track ID | Splash: "Track that person in the red shirt" |
| **Attribute Match** | Lightweight classifier filters by color/feature | Splash: "Track anyone wearing BLUE armband" |
| **Anomaly Detection** | Flag target with velocity vector deviating from crowd average | Splash: "Someone is running toward the protected player" |

### 6.5 Re-Identification After Occlusion
When ByteTrack loses a target (total occlusion), use:
1. **Hold last known trajectory vector**
2. **Execute expanding spiral search** (drone orbits wider)
3. **Re-match using HSV histogram** (Bhattacharyya distance < 0.35)
4. **Restore Track ID** when match found

## 7. 🟡 Depth Estimation — Range Finding Without LiDAR

### 7.1 Why Depth Matters for Splash
Splash needs to know distance to target for:
- **Fire decision**: Only fire when target is within 3m effective water stream range
- **Approach control**: Don't fly too close to target
- **Altitude adjustment**: Maintain optimal firing altitude (2-3m)

### 7.2 Monocular Depth Estimation — The Lightweight Solution

**Depth Anything V2 (Small)** — 25M parameters — is the best option for Splash:

| Model | Params | Edge Hardware | Boundary Quality | Metric Scale? |
|-------|--------|---------------|-----------------|--------------|
| **Depth Anything V2 (Small)** | **25M** | Jetson Orin Nano / RPi 5 + Hailo | Very Good | Yes (metric variant) |
| Apple Depth Pro | ~300M+ | Heavy companion computers only | Exceptional | Yes (zero-shot) |
| MiDaS v3.1 Lightweight | ~10-30M | Ultra-low-power processors | Soft/blurry edges | No (relative only) |

### 7.3 Splash-Specific Strategy
**Depth Anything V2 is too heavy for real-time on MacBook alongside YOLOv11n + tracking + servo control.** Alternative approaches for Splash:

1. **Altitude + Camera Geometry**: With known drone altitude (from barometer/GPS) and camera pitch angle, approximate ground distance using pinhole camera model. This is the lightest approach.
2. **Bounding Box Size Heuristic**: Person bounding box width correlates with distance. Calibrate: `distance ≈ k / bbox_width`.
3. **ArduPilot Rangefinder**: Add a VL53L1X ToF sensor ($3, 1g) for accurate short-range (<4m) measurements. Already planned as part of optical flow setup from May 22 research.
4. **Depth Anything V2 offline**: Run depth estimation on recorded footage for post-flight analysis and targeting accuracy evaluation.

### 7.4 Recommendation
For real-time Splash fire control: **Use bounding box size heuristic + VL53L1X rangefinder**. The VL53L1X provides accurate <4m measurements, which is exactly Splash's firing range. For targeting at longer ranges (identification/tracking), the bounding box heuristic is sufficient — Splash doesn't need centimeter precision, just "close enough to fire."

## 9. 🟡 Optical Flow for Motion Prediction

### 9.1 Lucas-Kanade Sparse Optical Flow
OpenCV's `cv2.calcOpticalFlowPyrLK()` provides sparse feature tracking that can:
- Track specific points on a person between frames
- Predict next position based on flow vectors
- Detect when target changes direction

### 9.2 Splash Application
- **Motion prediction**: Flow vectors on target bounding box center predict next frame position — feeds Kalman filter prior
- **Velocity estimation**: Average flow magnitude gives target speed — used for lead calculation in firing
- **Stationary detection**: Low flow magnitude = stationary target = fire decision (easier shot)

### 9.3 Integration with Kalman

## 12. Key Facts for Holographic Memory

1. **YOLOv11n (CoreML) achieves 125-145 FPS on MacBook M3** — 5% faster than YOLOv8n on Apple Neural Engine despite higher base latency. YOLOv11n's C2PSA attention block provides +2.2% mAP and better occlusion handling. Model is 5.4MB (2.6M params) — 13% smaller than YOLOv8n. This is the Splash CV detection backbone.

2. **ByteTrack is the superior multi-person tracker for drone top-down views** — outperforms DeepSORT and StrongSORT for aerial tracking because (a) it keeps low-confidence detections during occlusion, (b) it doesn't rely on appearance Re-ID which fails from above (everyone looks like head+shoulders), and (c) it has negligible compute overhead (IoU matching only). Combined with a priority score function (P = w1·Sconf + w2·(1-Dcenter) + w3·IIoU) for primary target selection.

3. **maxboels/TrackingPanTiltCam is the single most relevant open-source reference for Splash** — provides production-ready YOLOv8 + Kalman + PCA9685 servo turret with motion compensation. Turret mode (3-frame history, exponential weighting) matches Splash's auto-aim requirements exactly. Adaptable from MG996R to MG90S servos and from YOLOv8 to YOLOv11n.

4. **Three-layer motion compensation prevents tracking feedback loops**: (1) IMU gyro feedforward calculates expected visual shift from camera rotation, (2) optical flow subtraction isolates target motion from ego-motion, (3) hysteresis deadband prevents servo jitter from sub-pixel noise. Without this, pan-tilt tracking on a moving drone oscillates uncontrollably.

5. **HSV color filtering with adaptive thresholding + CLAHE + histogram backprojection provides robust team identification** from drone footage. Red requires dual masks (0-10 and 170-180), blue is single range (100-130). Bhattacharyya distance < 0.35 for re-identification after occlusion. Lighting robustness requires dynamic V_min based on frame average brightness.

6. **Depth Anything V2 (Small, 25M params) is the best monocular depth model for drones** but too heavy for real-time alongside YOLOv11n + tracking. Splash uses bounding box size heuristic (distance ≈ k / bbox_width) + VL53L1X ToF sensor (<4m) for firing range decisions. Depth Anything V2 reserved for offline accuracy analysis.

7. **MediaPipe Face Detection is unsuitable for Splash** — requires 1-2m close-up range. At drone altitudes (2-10m), facial features blur. YOLO whole-body detection is the correct approach. ESP32-S3 cannot run YOLO (SRAM too small). Splash architecture: ESP32-CAM streams MJPEG → MacBook M3 runs full CV pipeline → servo commands via MAVLink.
