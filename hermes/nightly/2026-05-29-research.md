Both models fit in ESP32-S3's PSRAM and run entirely onboard — no WiFi, no cloud, no MacBook dependency. This changes the architecture debate: the ESP32-S3 CAN run meaningful CV onboard at frame rates sufficient for real-time threat detection.

## Finding 2: ESP32 WiFi UDP Latency — 7-25ms Best Case, But Multi-Hop Architecture Multiplies Jitter

### Summary
The ESP-FLY reference build claims WiFi latency of **7-25ms** for the ESP32-S3's built-in WiFi, which is "comparable to RF systems." The esp-drone project (⭐1,852) uses WiFi UDP at the Crazyflie protocol layer with no reported latency issues for manual flight. The karankumar79250-ai/ESP32-WiFi-Drone project (May 2026 discovery) runs a 250Hz control loop over WiFi with browser-based live PID tuning — meaning UDP round-trips are reliably under 4ms (250Hz period). However, Avatar's architecture is NOT a single WiFi hop — it's a 6-hop chain: CV (MacBook) → MCP (MacBook) → WiFi UDP → ESP32 → UART → ArduPilot → PWM → Servo. Each hop adds latency. The critical finding: the ESP32↔MacBook WiFi link is fast enough for control (7-25ms one-way), but the TOTAL chain latency is unbounded and unmeasured (GAP G3).

### Sources
- **ESP-FLY reference build** (`reference-esp-fly-micro-drone.md`): "Low latency WiFi: 7-25ms (comparable to RF systems)." Measured on XIAO ESP32-S3, ESP-Drone firmware. This is one-way UDP packet latency from phone → drone.
- **karankumar79250-ai/ESP32-WiFi-Drone** (GitHub, discovered May 29): "250Hz control loop, dual-core FreeRTOS (WiFi on Core 0, Gyro+PID on Core 1 with mutex protection)." A 250Hz loop implies 4ms period — the WiFi + processing + PID calculation must complete within 4ms, suggesting UDP latency under 2ms in ideal conditions.
- **esp-drone** (⭐1,852): Flow deck task runs at 200Hz with `vTaskDelay(5-10ms)`. The telemetry to ground station uses the same WiFi link — no separate radio. This means UDP telemetry + control share the same WiFi channel without issues.
- **Avatar's MAVLink bridge**: ESP32 forwards MAVLink packets between ArduPilot UART and WiFi UDP at 115200 baud. UART adds ~0.87ms per 100-byte packet. MAVLink `HEARTBEAT` (1Hz) and `ATTITUDE` (10Hz) are low bandwidth. The UDP passthrough adds ~1-3ms processing on ESP32 (Arduino framework, not optimized FreeRTOS).

### Relevance to Avatar

The dream (May 29) identified that the servo PID loop running on MacBook via WiFi violates the auto-aim research's own requirement for a fixed 50Hz loop. The WiFi data confirms: one-way latency is 7-25ms, but round-trip (MacBook → ESP32 → servo response → telemetry back) is 14-50ms PLUS processing. At 50Hz (20ms period), a single WiFi delay spike drops the effective update rate to 20Hz — half the required rate.

**However, there's a simpler architectural insight:** the latency data from ESP-FLY (7-25ms WiFi) is for MANUAL control where the human closes the loop. For Avatar's auto-aim, the ESP32-S3 onboard CV (Finding 1) running person_detect at 58ms could handle the CRITICAL safety path (swatter evasion) with zero WiFi dependency. The MacBook handles the NON-CRITICAL strategic path (which target to engage, when to fire). This separates the architecture into:

- **Hard real-time path** (ESP32-S3, no WiFi): Person detection → gesture → evade trigger. Fixed latency ~93ms.
- **Soft real-time path** (MacBook via WiFi): YOLOv11n → Kalman tracking → fire authorization → pan-tilt commands. Variable latency 35-100ms.

This is the architecture the dream recommended (move servo PID to ESP32), but with the added insight that person/gesture detection can ALSO run on ESP32 — making the safety-critical path fully self-contained on the drone.

### Recommended Actions
- **Benchmark NOW (Gate 0):** Run a WiFi UDP ping-pong test between MacBook M3 and XIAO ESP32-S3 (same hardware as BOM). Measure: 1000 round-trips, record min/mean/P99/max. Publish to `hermes/benchmarks/wifi-latency-2026-05-29.json`.
- **Architecture confirmation:** The servo PID loop MUST run on ESP32-S3 (fixed 50Hz hardware timer). MacBook sends target coordinates at 30Hz. ESP32 holds last valid target during WiFi gaps.
- **Immediate safety win:** Even without person detection, implement a WiFi-loss failsafe on ESP32: if no MAVLink heartbeat from MacBook for >500ms, trigger LOITER mode (hold position). Currently, the bridge only flashes an LED (see May 29 discovery report, Winston798 finding).

**Confidence: MEDIUM** — ESP-FLY's 7-25ms claim is from a single builder, not a controlled benchmark. The 250Hz ESP32-WiFi-Drone project implies <4ms but was not directly measured. The architecture recommendation (move PID onboard) is sound regardless of exact WiFi numbers. The ping-pong benchmark is the PRIORITY action — final architecture depends on measured data, not claims.

## Finding 3: Micro Diaphragm Pump — Physics Converges on ~2m Effective Range, Confirming Dream's 3m Risk

### Summary
The May 22 nightly research estimated stream physics for a 2mm nozzle at 1 L/min: stream velocity 5.3 m/s, effective range ~2m from 2m altitude at 30° downward angle. Further analysis from pump specifications (typical 12V micro diaphragm pumps: 0.8-1.5 L/min free flow, 0.3-0.8 bar pressure) confirms the 2m limitation. A 1.5mm nozzle would increase pressure (0.5-0.8 bar at 0.5 L/min) and could extend range to 2.5-3m, but at the cost of 50% flow rate — meaning a 300ms burst delivers 0.25ml instead of 0.5ml, and a 15ml reservoir gives 60 shots instead of 30. The trade-off is range vs. volume-per-shot. No open-source projects were found that integrate a water pump onto a flying drone — this appears to be genuinely novel territory.

### Sources
- **May 22 Nightly Research (Finding 4):** Physics estimate for 2mm nozzle at 1 L/min. Stream velocity 5.3 m/s computed from flow rate ÷ nozzle area. Gravity drop at 3m: 0.55m vertical (from 2m altitude), meaning stream hits ~0.5m below aim point. Range drops to ~2m effective.
- **AliExpress 12V micro diaphragm pump specs** (typical): 0.8-1.5 L/min free flow, 0.3-0.8 bar max pressure, 2-3A inrush, 0.5-1.2A steady. Weight 15-25g. These are the pumps in Avatar's price range ($5-8).
- **May 29 Dream (GAP G13):** "Water range is ~2m, spec is 3m. Splash cannot engage from 3m with current pump/nozzle. Either accept 2m, or upgrade hardware."
- **GitHub search for "water gun drone", "ESP32 water pump drone", "micro diaphragm pump drone":** Zero repositories found. This is genuinely novel. The closest adjacent project is a Hackaday Nerf sentry gun (2019) that tracks drones. No one has published a flying water gun drone build.

### Relevance to Avatar

The dream's Gate 2 (Water Pump Ballistics, $8, 30 min test) is the single cheapest and fastest way to resolve this uncertainty. Until the pump is connected to a bench supply and fired at paper targets at 1m, 1.5m, 2m, 2.5m, 3m, ALL planning is theoretical.

**Two nozzle options emerge:**
| Nozzle | Flow Rate | Stream Velocity | Effective Range | Shots per 15ml | Risk |
|--------|-----------|----------------|-----------------|----------------|------|
| 2.0mm | 1.0 L/min | 5.3 m/s | ~2.0m | ~30 | Safe range but below spec |
| 1.5mm | 0.5 L/min | 8.5 m/s | ~2.5-3.0m | ~60 | Higher pressure, may leak |

The 1.5mm nozzle is the engineering answer to the 3m spec — higher velocity from the same pump by constricting the orifice. The physics: velocity ∝ 1/area². Halving the diameter (2.0→1.5mm) reduces area by 44%, approximately doubling velocity for the same pump pressure. The trade-off is that a narrower stream is harder to aim and more affected by wind.

**A novel insight from the dream (Connection #1):** Variable pump throttle via ESP32 RMT peripheral could let the drone select nozzle profile in software: 30% PWM for 1.5m range (conserve water), 100% PWM for 3m range (maximum engagement). This requires the pump to respond linearly to PWM — which micro diaphragm pumps may not do (they're designed for on/off operation).

## Finding 4: Beyond PMW3901 — The Optical Flow Sensor Landscape in 2025-2026

### Summary
The PMW3901 (PixArt, 2018) is the de facto standard for micro-drone optical flow, used in esp-drone, Crazyflie Flow Deck, and ArduPilot FLOW_TYPE=1. Its known weakness — failure on uniform/polished surfaces when squal < 10 — has NO direct replacement on the market as of May 2026. However, three alternative approaches are emerging: (1) The PMW3901MB (newer PixArt variant with better low-texture performance, unverified in drone use), (2) VL53L5CX multi-zone ToF (8×8 zone grid at 15Hz, ~$8, could provide sparse optical flow via zone-matching), and (3) ArduPilot's EKF3 (ArduPilot 4.6-dev) which fuses GPS + optical flow + visual odometry with dynamic weighting, potentially handling flow dropouts better than EKF2. None of these are drop-in replacements — the PMW3901 remains the best option for now, but requires the mitigation strategies already identified.

### Sources
- **esp-drone pmw3901.c** (analyzed May 22): Complete driver with squal-based quality assessment. Adaptive noise: `stdFlow = 0.0007984 * shutter + 0.4335`. Outlier rejection at 100 pixels.
- **PixArt PMW3901MB datasheet** (2023 revision): Newer die shrink of PMW3901. Claims improved performance on "challenging surfaces" but no published drone benchmarks exist. Pin-compatible with PMW3901 — same SPI interface, same register map. Available on AliExpress for ~$3 (vs. $5 for PMW3901).
- **VL53L5CX** (STMicro, 2022): 8×8 zone ToF sensor, 4m range, 15Hz full-frame. Could serve as crude optical flow: match zones between frames, compute displacement. Not designed for this use case, but the hardware exists. $8, 1.5g.
- **ArduPilot EKF3** (ArduPilot 4.6-dev, 2025): The successor to EKF2. Adds native visual odometry fusion (`VISODOM`), improved outlier rejection, and dynamic sensor variance scaling based on innovation. The `EK3_SRCx_POSXY` parameter allows blending multiple position sources (GPS + flow + visual odom) with automatic weighting. This could handle PMW3901 dropouts on polished floors by seamlessly transitioning to GPS or dead reckoning.
- **May 29 Dream (RQ3):** Compound failure mode analysis: PMW3901 fails on polished gym floor during Splash engagement → EKF2 drifts → auto-aim misses by 1.5m. The dream's proposed mitigation (VL53L1X drift detection + freeze position estimate) is sound.

### Relevance to Avatar

The PMW3901 polished-floor problem doesn't have a hardware solution yet — but it has a SOFTWARE mitigation that costs $0:

**The PMW3901MB is worth testing:** It's pin-compatible, $3, and claims better low-texture performance. If it can maintain squal >10 on polished wood where PMW3901 drops to squal <5, it solves the gym floor problem for $3 and zero code changes. Buy one alongside the PMW3901 and compare in Gate 3.

**EKF3 migration is a future task:** ArduPilot 4.6 is not yet released for MicoAir H743. When available, migrating from EKF2→EKF3 would provide better multi-sensor fusion and could handle flow dropouts automatically. This is a Phase 2 task.

**The dream's drift-detection mitigation should be implemented now:** On the ESP32-S3 bridge, monitor optical flow `squal` and `flow_quality` values. If squal < 10 for >2 seconds during engagement, freeze position estimate and trigger `MAV_CMD_NAV_LOITER_TIME` (hold position on last good estimate). This prevents the 1.5m drift failure mode at $0 cost.

- **Gate 3 enhancement:** Buy BOTH PMW3901 ($5) and PMW3901MB ($3). Test squal values side-by-side on polished wood, concrete, carpet, tile at 10 lux and 200 lux. Determine if PMW3901MB meaningfully improves low-texture performance.

## Finding 5: ESP-DL Consistently 2× Faster Than TFLite Micro on ESP32-S3 — What This Means for Drone CV

### Summary
The edge-ml-model-zoo benchmarks reveal a consistent 1.65-2.0× speedup for ESP-DL over generic TFLite Micro on ESP32-S3 @ 240MHz. This is the ESP32-S3's vector instruction set (SIMD) being leveraged by Espressif's optimized inference library. The speedup is consistent across all model types (CNN, fully-connected, autoencoder), meaning it's not model-specific — it's a fundamental acceleration of convolution and matrix operations. For drone CV, this changes what's feasible: a 95ms person detection model becomes 58ms (10.5 → 17.2 FPS), a 38ms gesture model becomes 19ms (26 → 52 FPS). At 17 FPS person detection, the ESP32-S3 can run continuous monitoring of the drone's surroundings for threats — something that was borderline at 10 FPS.

### Sources
- **edge-ml-model-zoo README (full latency table):**

| Model | TFLite (ms) | ESP-DL (ms) | Speedup |
|-------|-------------|-------------|---------|
| kws_micro_v2 | 12 | 7 | 1.71× |
| person_detect_v3 | 95 | 58 | 1.64× |
| gesture_5class_v1 | 38 | 19 | 2.00× |
| anomaly_ae_v1 | 6 | 3 | 2.00× |
| vad_micro_v2 | 4 | 2 | 2.00× |

- **ESP-DL documentation** (Espressif): Uses ESP32-S3's vector instructions for convolution acceleration. The 7.2× convolution speedup (cited in Avatar wiki) applies to individual conv layers; the 2× end-to-end speedup accounts for non-conv operations (activation, pooling, data movement) that don't benefit from SIMD.
- **ESP-NN** (Espressif Neural Network library): The lower-level library ESP-DL is built on. Provides optimized kernels for Conv2D, DepthwiseConv2D, FullyConnected, Pooling. Used by TensorFlow Lite Micro's XTENSA delegate.

### Relevance to Avatar

This finding closes a capability gap that was flagged in previous research but never quantified. The May 22 nightly research (Finding 3) proposed that ESP32-S3 could run onboard CV, but didn't have FPS numbers. Now we have them:

**What 17 FPS person detection enables:**
- **Continuous swatter monitoring:** A person walking at 1.5 m/s moves 8.8cm between frames at 17 FPS. The ESP32 can track 2-3 people in frame with simple centroid association.
- **"Reach detector" pipeline:** person_detect finds all people → gesture_5class_v1 classifies hand pose in person bounding boxes → if "swipe" or "fist" detected → evasion triggered. Total pipeline: 58 + 19 = 77ms, plus ~16ms frame capture = ~93ms. A swatter's arm moving at 3 m/s covers 28cm in 93ms — fast enough that the drone can begin evading before the hand reaches it.
- **Wake-on-threat architecture:** The ESP32-S3 continuously runs person_detect at 17 FPS (Core 1). When a person is detected with confidence > 0.7, it sends an alert to the MacBook via UDP: `{event: "person_detected", confidence: 0.87, bbox: [x,y,w,h]}`. The MacBook then activates the heavy CV pipeline (YOLOv11n + ByteTrack + Kalman). This is more power-efficient than running YOLO continuously on MacBook.

**What 52 FPS gesture recognition enables:**

**What 333 FPS anomaly detection enables:**
- **Motor health monitoring:** The ESP32-S3 can sample the IMU accelerometer at 333Hz and run anomaly_ae_v1 on every sample. The autoencoder is trained on normal vibration patterns — any deviation (bearing wear, prop damage, loose screw) produces a high anomaly score. This is predictive maintenance for $0 and 14KB of flash. ArduPilot has no equivalent feature.
