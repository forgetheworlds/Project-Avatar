## I. Connection Synthesis — Non-Obvious Links Across Accumulated Knowledge

### 1. DroneServer MCP Safety Patterns → Avatar's MCP Server (Salvaged Research)

**What was found** (May 4, Finding 1): DroneServer (PeterJBurke/droneserver) is a 3,350-line battle-tested MCP server for LLM→drone control. Its safety architecture is the most valuable artifact: Takeoff Altitude Wait (blocks navigation until altitude reached), Landing Gate (blocks landing if >20m from destination), monitor_flight (mandatory 30-second progress updates), and a crash post-mortem documenting how `pause_mission()` caused a 25m fall because LOITER mode behaves differently without an RC controller.

**What Avatar has now**: A 13-tool MCP server (`splash/control/mcp_server.py`) with tools: arm, takeoff, land, goto, orbit, get_telemetry, get_camera_feed, identify_target, engage_target, protect_mode, disarm, rtb. State machine: IDLE → ARMED → FLYING → ORBITING → ENGAGING → RETURNING.

**The connection — DroneServer patterns Avatar MUST adopt:**

| DroneServer Pattern | Avatar Status | Risk if Missing |
|---|---|---|
| **Takeoff Altitude Wait** — blocks navigation until >2.5m reached | ❌ Not documented in current MCP server | Navigation at <1m altitude → collision with obstacles/people |
| **Landing Gate** — blocks landing >20m from registered destination | ❌ Not implemented | LLM could land drone on a roof, road, or person instead of home |
| **monitor_flight** — 30s mandatory progress; LLM can't "get bored" | ❌ Not implemented | LLM may stop calling tools after 5-10 min (DroneServer documented this) |
| **Flight mode transition verification** — every altitude behavior tested before hardware | ❌ No mode transition tests documented | The LOITER crash happened because LOITER mode altitude behavior differs from GUIDED — same class of bug possible with ArduPilot mode transitions |

**Actionable insight**: Avatar's MCP server already has the tool structure. Adding DroneServer's safety gates is a SOFTWARE-ONLY upgrade — no hardware changes needed. The `takeoff()` tool should: (1) send MAV_CMD_NAV_TAKEOFF, (2) poll `get_telemetry()` at 1Hz until altitude > target-0.5m, (3) return `{"safe_to_navigate": true}`. The `land()` tool should: (1) check current position vs home position (haversine), (2) BLOCK if >20m away with explanation, (3) wait for `landed_state == ON_GROUND` + stable for 3 seconds before returning success.

**Confidence: HIGH** — DroneServer code was cloned and analyzed. Patterns are protocol-agnostic (work with MAVLink as well as they worked with MAVSDK).

### 2. The Two-Tier Vision Architecture Was Right — And Now It's Even More Natural

**What the May 2 dream proposed**: Two-tier vision — ESP32-S3 onboard blob/ArUco tracking (Tier 1, 20Hz, <10ms latency) + MacBook YOLO person detection (Tier 2, 2-5Hz, >100ms latency). Inspired by human peripheral vs foveal vision.

**What changed**: The May 2 dream assumed ESP32-S3 was the flight controller, running at near 100% CPU. The pivot fixes this — ESP32 is now a WiFi bridge with spare cycles. The MacBook already runs both the MCP server AND the CV pipeline (`splash/cv/` with YOLOv8 + ByteTrack + HSV color filtering).

**The connection — the two-tier approach is now TRIVIAL to implement**:
```
ESP32-S3 (Tier 1 — 20Hz, <10ms latency):
  - Color blob tracking: simple HSV threshold on JPEG frames from Hawkeye Thumb
  - ArUco marker detection: targets wear ArUco armbands
  - Optical flow frame-to-frame motion: direct from camera feed
  - Sends: {bbox_cx, bbox_cy, bbox_area, lost_tracking} via UDP (50 bytes)
  
  This runs ENTIRELY ONBOARD, needs no MacBook, works at <10ms latency.
  If the MacBook WiFi drops, Tier 1 maintains tracking lock.

MacBook M3 (Tier 2 — 5Hz, >100ms latency):
  - YOLOv8n person detection + ByteTrack multi-target
  - HSV jersey color filter → team identification
  - Shot composition scoring (rule of thirds, target size ratio)
  - Fire logic: distance < 3m AND bbox centered
  - Mission planning: orbit radius, engagement sequence

  The MacBook is the "director" — it says "engage target #3" and
  the ESP32 handles the fast inner loop of keeping that target centered.
```

**Why this is different from the current CV pipeline**: The current `splash/cv/` pipeline runs entirely on MacBook — every frame must traverse ESP32→WiFi→MacBook→CV→MCP→WiFi→ESP32→ArduPilot. That's 150-250ms round-trip. Moving the color/blob tracking to ESP32 cuts the inner loop to <10ms. The MacBook only intervenes for high-level decisions (new target, change orbit, fire authorization).

**Confidence: MEDIUM-HIGH** — ESP32-S3 ArUco detection benchmarks exist, and simple HSV blob tracking is well within ESP32 capabilities. The two-tier pattern is inspired by the human visual system and proven in robotics (e.g., Boston Dynamics' Atlas uses a similar fast/slow perception split).

### 3. Cinematic Trajectory Research → Splash Combat Maneuvering

**What was found** (May 2, Finding 1 + May 4, Finding 5): Rich research field on cinematic trajectory generation — ACDC (arXiv 2509.16176) for NL→drone video tours, CineMPC for composition cost functions, minimum-snap for smooth waypoint sequences. The research was done for cinematic filming (follow a snowboarder, orbit a subject).

**What Avatar does now**: Splash mission — protection mode (orbit and fire on intruders), engagement mode (approach and fire). The `cinematic_shots.py` in the archive (16 shot templates) was for the original Mark4 7" build, now archived.

**The connection — combat maneuvering IS cinematic maneuvering with different constraints**:

| Cinematic Concept | Splash Combat Equivalent |
|---|---|
| **Rule of thirds positioning** | Optimal firing angle (target at frame center = gun aligned) |
| **Lead room** (space ahead of moving target) | Intercept trajectory (aim where target WILL be, not where they ARE) |
| **Smooth orbit** around subject | Protection orbit with variable radius (tighten when target approaches) |
| **Slow reveal** shot | Ambush from behind cover, rapid approach, fire, retreat |
| **Minimum-snap trajectory** | Jerk-limited evasive maneuvers (smooth dodging looks cooler AND saves battery) |
| **CineMPC composition cost $J_{im}$** | Fire solution cost: penalize deviation from center-crosshair, penalize being >3m away, reward target centered AND close |
| **Occlusion constraint** (don't fly behind trees) | Cover constraint (stay behind pillars/walls until engagement window opens) |

**Actionable insight**: The CineMPC cost function framework can be adapted as a "combat quality" scorer. Instead of penalizing deviation from rule-of-thirds grid, penalize deviation from optimal firing position:
```python
def combat_cost(drone_pos, target_pos, target_velocity):
    distance = norm(drone_pos - target_pos)
    aim_angle = angle_between(drone_forward, target_pos - drone_pos)
    lead_error = norm(target_pos + target_velocity * time_to_hit - drone_pos)
    
    J_distance = max(0, distance - 3.0) * 10     # Penalize being >3m
    J_aim = abs(aim_angle) * 5                     # Penalize off-center aim
    J_lead = lead_error * 2                        # Penalize not leading target
    
    return J_distance + J_aim + J_lead
```

This converts "cinematic trajectory optimization" into "combat engagement optimization" with zero new research — just different weights on the same cost terms.

**Confidence: MEDIUM** — The math is sound and CineMPC's cost function framework is modular by design. But this is conceptual — no one has published "combat drone trajectory optimization" in the open literature. Avatar would be generating novel applied research.

### 4. The PMW3901 Research Gap Now Bites Harder

**What was found** (May 2, Finding 4): PMW3901 optical flow fails on uniform surfaces (sand, asphalt, snow, water), at altitudes >4m, and in low light. Position drift is 0.1-0.5 m/s without GPS correction.

**What Avatar has now**: The current build ($312 BOM) has NO optical flow sensor. Position hold relies entirely on GPS (GOKU GM10 Nano V3). For outdoor campus use, this is fine. For indoor Senior Assassins (corridors, gymnasiums, classrooms), there is ZERO position hold capability.

**The connection — indoor play is where Splash is most likely to be used**: Senior Assassins is a school-based game. Most engagements happen in hallways, common areas, and near building entrances. These are GPS-denied environments. Without optical flow or a comparable indoor positioning system, the drone CANNOT maintain position indoors — it will drift with every air current and prop wash reflection.

**What the research actually says we need for indoor Splash**:
- PMW3901 optical flow ($10, 1g) — horizontal velocity
- VL53L1X ToF rangefinder ($5, 1g) — altitude reference
- Combined weight: ~2-3g, cost: ~$15
- Proven in: LiteWing, Crazyflie Flow Deck, PX4 optical flow builds

**Architecture integration**: ArduPilot supports optical flow via EKF2 fusion. The PMW3901+VL53L1X connects to ArduPilot's UART/I2C and provides `vision_position_estimate` and `vision_speed_estimate` MAVLink messages. The EKF2 fuses optical flow + IMU + barometer for drift-free position hold. This is a CONFIGURATION change, not a code change.

**Confidence: HIGH** — PX4/ArduPilot optical flow docs are definitive. The sensors are commodity hardware. This is a known, solved integration, not research.

### 5. Greta's 2-Year Failure Log → Predictive Maintenance for a Brushless Build

**What the May 2 dream identified**: The Greta project logged 2 years of failures: 52 props, 7 arms, 6 legs, 2 Pixhawks, 2 Jetsons, multiple ESCs/motors. Each failure had a precursor. Avatar could train a lightweight anomaly detector on telemetry.

**What's different now**: The pivot to brushless motors + ArduPilot FC changes the failure profile. Brushless motors are more reliable than coreless (no brushes to wear). ArduPilot has built-in logging (dataflash logs at 1kHz). The failure precursors shift:

| Failure Type | Precursor (ArduPilot Log) | Detection |
|---|---|---|
| **Motor bearing wear** | MOT.RCOU output asymmetry >15% for level flight | Track `max(RCOU.C1..C4) - min()` per second |
| **ESC degradation** | ESC temperature rising, current ripple increasing | Track `ESC.temperature` and `BAT.Curr` variance |
| **Prop imbalance** | IMU.AccZ variance at motor frequency | FFT of IMU.AccZ, flag peaks at ~200-400Hz |
| **Battery aging** | Voltage sag slope steepening | Track dV/dt during hover, compare to baseline |
| **GPS interference** | HDOP increasing, satellite count dropping | Track `GPS.HDOP` trend over flights |
| **ESP32 WiFi degradation** | Packet loss increasing, RSSI dropping | Track UDP ACK round-trip time, RSSI per flight |

**Actionable insight**: ArduPilot dataflash logs contain ALL of these signals. A Python script on the MacBook that reads the last 10 flights' logs and computes baselines + trends could flag degradation BEFORE it causes a crash. This costs $0 and adds 0g — it's pure software on the ground station.

The May 2 dream proposed this for the micro-drone path — but it's MORE valuable for the brushless path because: (1) brushless builds fly longer (more data per flight), (2) ArduPilot logs are richer, (3) higher $312 investment means more to protect.

**Confidence: HIGH** — ArduPilot dataflash format is documented. The metrics are standard aerospace health monitoring concepts (HUMS — Health and Usage Monitoring Systems). This is a software-only feature.

### RQ2: What is the actual round-trip latency of the MacBook→ESP32→ArduPilot→ESP32→MacBook control loop?

**Context**: The Splash engagement pipeline is:
```
MacBook CV detection → MCP tool call → JSON → UDP → ESP32 → UART → ArduPilot → motors respond
ArduPilot telemetry → UART → ESP32 → UDP → MacBook → CV confirms target hit
```

Each hop adds latency. At 5 m/s target speed (a running student), every 100ms of latency = 50cm of target movement. The cinema.md document (for the original Mark4 build) acknowledged 150-250ms total pipeline latency.

**What's different now**: The ESP32 is now a MAVLink bridge (not FC), adding a UART hop (115200 baud = ~1ms per MAVLink message at typical sizes). ArduPilot's inner loop is 400Hz but the MAVLink telemetry stream is 10-50Hz. The WiFi hop is still 10-20ms best-case, 50-100ms worst-case.

**What we need to measure**: Instrument the MCP server to log timestamps at each stage:
```python
t0 = time.monotonic()  # before MCP tool sends command
# ... UDP send
t1 = telemetry.ack_timestamp  # ESP32 confirms receipt
t2 = telemetry.position_updated  # ArduPilot reports new position
round_trip = t2 - t0
```
Run 100 iterations, compute p50/p95/p99 latency. This is a 1-hour engineering task that answers a fundamental architectural question.

### RQ3: Can ArduPilot's native spline waypoint and orbit commands match custom trajectory generation quality?

**Context**: The cinematic trajectory research (May 2, Finding 1) explored ACDC, CineMPC, minimum-snap, and drone-pathgen — all assuming CUSTOM trajectory generation running on the MacBook, sending position/velocity setpoints at 20Hz. With ArduPilot as the FC, Avatar can instead use ArduPilot's NATIVE commands:
- `MAV_CMD_NAV_SPLINE_WAYPOINT` — cubic spline through waypoints (smooth by definition)
- `MAV_CMD_NAV_LOITER_TURNS` — orbit at specified radius, speed, direction
- `MAV_CMD_DO_CHANGE_SPEED` — speed changes during mission
- `MAV_CMD_NAV_LOITER_TIME` — hover at position for N seconds

**The question**: Is ArduPilot's spline waypoint + orbit good enough for cinematic-quality flight (combat or otherwise), or does Avatar still need custom minimum-snap trajectory generation on the MacBook?

**Experiment**: Compare three approaches in SITL simulation:
1. **ArduPilot native**: Send 5 spline waypoints, let ArduPilot interpolate
2. **Custom minimum-snap**: Generate 50 smooth waypoints on MacBook, stream at 2Hz
3. **Hybrid**: MacBook plans the trajectory, ArduPilot executes spline waypoints

Measure: (a) path smoothness (jerk integral), (b) position tracking error (deviation from ideal path), (c) CPU usage on MacBook, (d) bandwidth (MAVLink messages per second). If ArduPilot native is within 10% of custom minimum-snap on jerk integral, Avatar saves weeks of development.

**Why this matters for Splash**: Smooth evasive maneuvers look more intimidating AND are more energy-efficient. Jerky drone motion wastes battery and looks amateur. If ArduPilot's native commands can produce smooth flight, the MacBook's role simplifies to "decide WHERE to go" rather than "compute HOW to get there."

### RQ4: What is the minimum safe engagement altitude for a water gun drone vs a human target?

**Context**: This is a physics + safety + game-design question that NO research has addressed. Splash fires water from a micro diaphragm pump at 12V. Variables:
- Pump pressure / stream velocity (unknown — needs ground test)
- Stream dispersal over distance (water breaks into droplets after ~1-2m)
- Safe drone altitude (FAA/Transport Canada: no specific minimum, but "don't endanger people")
- Target reaction time (can a person swat the drone at <3m?)

**The trade-off**: 
- Too high (>5m): Water disperses before reaching target, pump can't push water that far
- Too low (<1m): Drone is within arm's reach — target can grab/swat it, prop strike risk
- Sweet spot: probably 2-3m altitude, firing downward at 30-45° angle

**What we need**: Ground test with the actual pump, nozzle, and reservoir. Measure:
1. Stream distance at 12V: at what range does the stream break into mist?
2. Stream accuracy: what's the spread diameter at 2m, 3m, 5m?
3. Drone stability during pump activation: does the pump's recoil affect attitude?

This is not a research question for Hermes to answer from papers — it's a GROUND TEST for Muadh to perform before the first flight. But the dream should flag it as an unanswered safety question.

### 🟡 HIGH PRIORITY: ESP32 is Severely Underutilized — Offload Tier-1 CV to It

**Current state**: ESP32-S3 acts as a serial-to-UDP bridge. It reads MAVLink from ArduPilot's UART, wraps it in UDP, sends to MacBook. It receives UDP commands from MacBook, unwraps to MAVLink, sends to ArduPilot. This is ~5% of the ESP32-S3's capability.

**What the ESP32-S3 CAN do (validated by research)**:
- 240MHz dual-core Xtensa LX7
- AI acceleration instructions (ESP-NN)
- 8MB PSRAM (enough for frame buffers)
- WiFi at 150Mbps
- Camera interface (if using ESP32-CAM variant or separate camera module)
- Color blob tracking at 30+ FPS (simple HSV thresholding)
- ArUco marker detection at 10-15 FPS
- Optical flow computation from camera feed

**Proposed architecture**:
```
ESP32-S3 (reimagined role):
  Core 0: WiFi stack + UDP server + MAVLink bridge
  Core 1: Tier-1 CV (color tracking / ArUco / optical flow)
  
  Sends to MacBook (via UDP): {target_x, target_y, target_size, confidence, fps}
  This is 50 BYTES per frame vs 50KB for a JPEG frame.
  
  The MacBook STILL runs YOLO for person detection and mission planning,
  but the fast inner loop (keep target centered) runs on ESP32.
```

**Impact**: Latency for the inner tracking loop drops from ~150ms (MacBook round-trip) to <10ms (ESP32 onboard). This is the difference between "drone reacts to where the target WAS 0.75m ago" and "drone reacts to where the target IS."

**Cost**: $0 additional hardware (ESP32-S3 is already in the build). Software complexity: moderate (need to write ESP32 CV code in C/ESP-IDF, not Python). Worth it for the latency improvement.

### 🟢 MEDIUM PRIORITY: The ELRS Backup Path is Under-Documented

**Architecture** (from BLOCKERS): ELRS Nano RX at $15, controlled by a physical RC radio. This bypasses the ESP32 entirely — direct RC → ArduPilot.

**The good**: This provides a hardware failsafe. If ESP32 WiFi drops or the MacBook crashes, the pilot grabs the RC and takes manual control. This is EAXCTLY what the May 2 dream recommended.

**The gap**: Nowhere is it documented HOW the ELRS backup integrates with the MCP server. Questions:
1. Does the MCP server DETECT when manual RC control takes over? (ArduPilot broadcasts `HEARTBEAT` with `base_mode` reflecting current control source.)
2. Does the MCP server YIELD control gracefully? Or does it fight the RC pilot?
3. Is there a physical switch to toggle between "autonomous" and "manual" modes?
4. What happens if the LLM issues a `takeoff()` command while the RC is in control?

**Recommendation**: Add an `rc_override` state to the MCP state machine. When ArduPilot reports `base_mode` with manual control active, the MCP server transitions to `RC_CONTROLLED` state and BLOCKS all autonomous commands (arm, takeoff, goto, engage_target). Only `disarm` remains available. When RC control ends (pilot switches back to autonomous mode), MCP server transitions back to previous state (FLYING/IDLE).
